# 디톡스메이트 정책 작성·수정

## 발동 조건

요청과 대화 맥락에서 제품 기획·정책 문서를 작성하거나 변경하려는 의도가 드러날 때 적용한다. ‘기획’, ‘정책’이라는 단어를 반드시 포함할 필요는 없지만, 기능 동작·이용 조건·공개 범위 등 팀이 합의한 제품 규칙을 기준 문서에 반영하는 작업이어야 한다.

- 적용: ‘친구 수락 정책을 위키에 반영해 줘’, ‘앱 잠금 기능의 기획 문서를 정리해 줘’.
- 제외: ‘데이터팀 v2 아래에 가설과 지표 문서를 만들어 줘’, 회의록·조사 결과·분석 계획 등 일반 문서의 작성·수정·이동.
- Notion·위키·v2·문서라는 표현이나 앞서 기획·정책을 조회했다는 사실만으로 발동하지 않는다. 일반 문서에는 정책 DB 위치·정책 템플릿·변경이력 규칙을 적용하지 않는다.
- 기획·정책 조회만 요청한 경우에는 `fetch-notion-wiki`를 사용한다. 제안·검토만으로 Notion을 변경하지 않는다.

## 원본 위치

- 문서 DB: https://www.notion.so/04b8dff159e44753960b2d950ef6c5f5
- 데이터 소스: `0656dd97-8a58-47c1-84f0-edea13a3ce31`
- 현재 정책 템플릿: https://www.notion.so/3ecad7a38ce580a7a8e6c29eb7b33bd1 (`정책 template_v1`)

Notion 템플릿 본문이 문서 형식의 원본이다. 과거 대화나 Skill에 복사해 둔 목차로 대체하지 않는다. 템플릿 ID가 더 이상 DB에 등록되어 있지 않으면 DB의 현재 템플릿 목록을 확인한다. 후보가 여러 개이고 기본값이나 요청으로 구분할 수 없을 때만 선택을 묻는다. 템플릿을 읽을 수 없으면 작성 초안까지 준비하고 실제 반영은 진행하지 않는다.

## 작업 범위

사용자가 요청한 생성·수정 범위 안에서 바로 작업한다. 이미 반영을 요청한 변경에 별도 승인자를 요구하지 않는다. 제안·검토만 요청한 경우에는 초안을 제시한다. 정책 자체의 의미가 불명확하면 그 부분만 질문하고 명확한 부분의 준비를 진행한다.

기획과 정책을 기능별 한 문서로 관리한다. 공통 정책은 한곳에 정의하고 연결한다. 누구나 수정할 수 있으며 LLM 결과는 사람이 읽고 검수한다. 최신은 팀의 최근 합의를 뜻한다. 코드나 Figma에서 발견한 차이를 팀 합의로 간주하지 않는다.

## 준비

기본 연결은 팀용 내부 연결로 인증하는 `detoxmate-notion` CLI다. 먼저 [CLI 조회·수정 절차](references/notion-api.md)를 읽고 PATH 또는 `$HOME/.local/bin/detoxmate-notion`에서 실행 경로를 확인한다. 토큰은 로컬 실행 명령이 불러오며, 스킬에 인증정보나 특정 팀원의 컴퓨터 경로를 넣지 않는다. 토큰을 출력·복사하거나 로그인 명령을 실행하지 않는다. CLI가 없거나 인증·접근이 실패하면 원인을 알리고 초안까지만 준비한다. 다른 계정의 MCP로 조용히 전환하지 않는다. 사용자가 다른 연결 사용을 명시한 경우에만 그 연결의 실제 도구·스키마를 따른다.

1. DB의 현재 속성과 등록된 템플릿을 읽고, 사용할 템플릿 본문을 읽는다. 이름이 같은 일반 문서나 과거 템플릿을 혼동하지 않는다.
2. 기존 문서의 이름·다루는 범위로 대상과 중복 문서 여부를 확인한다. 새 문서는 이 DB의 데이터 소스 안에 만든다. 기존 문서는 소속과 현재 본문을 먼저 확인한다.
3. 필요한 문서만 선별한다. `fetch-notion-wiki`가 설치되어 있으면 그 선택 절차를 사용한다. 없더라도 DB 목록 → 대상 본문 → 영향이 있는 관련 문서 순서로 읽을 수 있다. 모든 문서를 모으지 않는다.
4. CLI의 현재 REST API 스키마와 Markdown 형식을 확인한다. MCP의 평면 속성 형식이나 `command` 인수를 REST 요청에 그대로 보내지 않는다. 목록·템플릿·본문을 읽었다는 사실만으로 쓰기 권한까지 검증됐다고 하지 않는다.

## 작성

- 현재 템플릿의 고정 Heading을 유지하고, 행동·주제별 소제목은 기능에 맞게 구성한다. 페이지 제목을 본문 H1로 반복하지 않는다. 고정 섹션은 H2, 섹션 안의 행동·주제는 H3로 구분한다. 안내 문장은 실제 내용으로 대체한다. 템플릿 개정 제안을 실제 적용된 형식으로 간주하지 않는다.
- 작성 안내는 해당하는 내용만 점검하는 기준이다. 모든 항목을 채우기 위해 불필요한 섹션이나 정책을 만들지 않는다. 사용자뿐 아니라 시스템·운영자의 동작도 제품 정책에 해당하면 포함한다. 조건·결과·분기·예외는 해당 행동 옆에 적는다.
- 여러 흐름에 적용되는 공통 원칙, 공개 범위, 운영자 처리 등은 필요하면 독립된 H3 주제로 묶는다. 역할·상태별 차이가 많으면 표로 정리한다. 이를 모든 문서의 필수 목차로 만들지는 않는다.
- 제품 동작과 디자인 표현·기술 설계를 구분한다. 예를 들어 ‘확인 없이 즉시 거절한다’, ‘관계 해제 후에도 댓글을 유지한다’, ‘신고자·대상·시각·처리 상태를 기록한다’는 정책이다. X 버튼·바텀시트 형태·정확한 안내 문구는 디자인 표현이고, 테이블의 1:N 관계·조회 구현 방식은 기술 설계다. UI 세부사항과 FE·BE·PD 구현 지식을 새로 덧붙이지 않고, 동작·공개 범위·정보 유지에 관한 정책은 보존한다.
- 같은 규칙은 기준이 되는 한곳에 정의한다. 다른 흐름에서는 필요한 맥락만 요약하거나 해당 주제·문서를 참조한다. 요청한 변경으로 직접 영향을 받는 기존 반복 서술은 함께 맞추거나 참조로 정리한다. 서로 다른 규칙이 충돌하면 임의로 하나를 선택해 통합하지 않는다.
- 근거 없는 숫자·조건·기한을 만들지 않는다. 아직 합의하지 못한 것은 미정 사항에, 제공하지 않기로 확정한 것은 범위 또는 기존 제외 사항에 적는다. 문서에 없다는 이유만으로 미제공 정책이라고 단정하지 않는다. 변경 이유 중 정책 이해에 계속 필요한 배경은 본문에도 남겨, 최신 한 건만 유지하는 변경이력 교체로 사라지지 않게 한다.
- Figma는 별도 섹션에 화면·흐름·상태 이름과 실제 제공되거나 확인한 링크를 둔다. 링크를 발명하지 않는다. 자료가 없으면 미연결로 표시한다.
- 문서명·구분·다루는 범위·관련 문서는 실제 DB 속성에 맞춰 채운다. 영향이 있는 문서만 연결하며, 자동 최종 수정일은 직접 쓰지 않는다.
- 최상단 변경이력은 최신 한 건으로 교체한다. 사용자의 현지 날짜와 무엇을 왜 바꿨는지 기록한다. 이유가 불명확하면 지어내지 않고 확인 필요로 표시한다.

## 반영과 검수

기존 문서는 요청한 정책과 직접 영향을 받는 부분을 수정한다. 전체 템플릿 재적용으로 본문을 중복 생성하거나, 작은 수정 때문에 기존의 다른 섹션을 삭제하지 않는다. 전체 형식 변환을 요청받았을 때만 내용 누락 없이 재구성한다. 기존 하위 페이지·DB·링크를 보존한다.

새 문서에 도구의 템플릿 적용 기능을 쓰는 경우, 적용 완료와 본문 생성을 확인한 뒤 편집한다. 기능이 없다면 방금 읽은 템플릿 구조로 내용을 작성한다. 응답이 불명확하거나 쓰기가 시간 초과되면 현재 상태를 조회해 반영 여부를 확인한 뒤 재시도한다. 확인 없이 같은 페이지를 다시 만들지 않는다.

초안 준비 중 대상이 수정됐을 가능성이 있으면 반영 직전에 다시 읽어 최신 내용을 기준으로 병합한다. 저장 후 해당 페이지를 읽어 실제 변경, 최신 변경이력, 미정과 확정된 제외 사항의 구분, 직접 영향을 받는 반복 서술의 일치, 유지해야 할 내용이 맞는지 확인한다. 기존 문서의 요청 범위 밖 UI·구현 내용이나 구조 문제는 임의로 삭제·재편하지 않고 필요한 정리만 제안한다. 권한·연결 문제로 저장할 수 없으면 초안과 미반영 범위를 알린다.

완료 시 변경한 문서 링크, 무엇을 바꿨는지, 남은 미정 사항을 짧게 보고한다. 사람이 검수할 수 있게 하되 실제로 검수했다고 표시하지 않는다. 정책 조회·수정 요청은 팀원에게 메시지를 보내거나 저장소에 코드를 수정할 권한까지 포함하지 않는다.
